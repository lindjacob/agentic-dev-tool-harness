# Writing Documentation

Documentation is agent-memory. Future agents are stateless — what isn't written down is lost. But
every doc that doesn't earn its keep is process noise.

## Reference direction

Docs vary in generality and stability — roughly:

```text
principles · ADRs · cross-area specs    general, stable, rarely change
package & feature READMEs                specific, volatile, change often
code comments                            most specific
```

This is an ordering, **not** a containment hierarchy: `docs/architecture/` and `docs/decisions/` are
siblings, not parent and child. The one durable rule is **reference direction**:

- A document may reference more-general / more-stable documents (a feature README cites the ADR or
  spec it implements).
- A document must **not** reference more-specific / less-stable ones (an ADR never names a feature
  file; a spec never names the component that implements it).
- **Index files are the sole exception** — an index exists to point down to its children.

This is what lets the docs scale without auto-maintenance: nothing general needs editing when
something specific changes.

Application READMEs (code folders, not `docs/`) may always reference `docs/` — that is an upward
reference — but they explain the code at their level. Link up to a principle; never restate it
locally.

Each doc must also be **self-contained at its grain** (complete for its level; cite upward for
binding context, don't re-inline it) and express **intent, not mechanism** (why it exists, what
invariants it preserves, what it deliberately does not do). If a doc could be regenerated by reading
the code, it's restating — rewrite or delete it.

## Explain the product, not just the mechanics

A fresh agent needs to know **what problem this repo solves and what value it delivers** — not only
how the code is laid out. Every repo's docs must carry that product/business "why" somewhere an
agent will find it (a top-level `docs/` overview or index). Mechanics without purpose leave an agent
optimizing the wrong thing.

## Decide before you write

Ask: _who reads this, and how often?_

- "Once at review then never" → don't write it. Put the reasoning in the commit message or PR body.
- "An agent picking up this code in three weeks" → write it.
- "An agent picking up _any_ issue in this repo" → write it.

## Where docs live

| Document | Where | When to add or update |
| --- | --- | --- |
| **Per-package README** | the package's root | New conventions, new public surface, or non-obvious build/run steps. |
| **Feature README** | the feature folder | The feature has ≥3 source files **or** a non-obvious cross-module interaction. Smaller features rely on header comments only. |
| **Nested `AGENTS.md`** | a subtree's root | The subtree has stack- or workflow-specific rules an agent must follow when editing inside it. Add when the first such rule appears, not preemptively. |
| **Root `AGENTS.md`** | repo root | Project-wide conventions, layout, top-level commands. |
| **ADR** | `docs/decisions/NNNN-…md` | Irreversible decision; the pattern other things follow. Use the `write-adr` skill. |
| **Spec under `docs/<area>/`** | an area folder | Cross-cutting business or system behaviour. Update when development surfaces a fact that refines it. |
| **Inline comment** | the code | Non-obvious intent, trade-off, or constraint the code can't convey. Never narrate what the code does. |
| **Rule** | the tool's rules location | Workflow imperative an agent must follow regardless of task. |
| **Skill** | the tool's skills location | Capability an agent applies for a specific task. |

## Feature README template

Three required sections. Each answers a question the code structurally cannot. Keep it short.

```markdown
# <feature name>

## Purpose

One paragraph: what user- or system-visible problem this solves, and why this feature exists rather
than not. Cite the product spec or ADR that motivated it.

## Invariants

Bulleted list: properties this feature must always preserve. The things that, if broken, cause
silent correctness failures.

## Non-goals & trade-offs

Bulleted list: deliberately out-of-scope behaviour, and the trade-offs embedded in the current
design.
```

No "Architecture", no "How it works", no "API reference" — those are the code's job.

## Updating docs as you learn

Development routinely surfaces facts that conflict with an upstream doc. Update **in the same PR** as
the code that prompted the learning.

- **Spec was vague; implementation made it precise.** Update the spec. No ADR.
- **Spec was wrong in a reversible way.** Update the spec. Note it in the PR body.
- **Spec was wrong in an irreversible way (changes how we build).** Amend the relevant ADR in place,
  or write a new ADR that supersedes it. Use the `write-adr` skill.
- **A new pattern emerged that other code should follow.** That's an ADR. Don't bury it in a README.

Never ship a PR with code that contradicts an unchanged upstream doc.

Drift that escapes per-PR discipline is caught later by the `audit-docs` skill.

## Doc volume budget

Docs should be a fraction of the code they describe.

- **ADR**: ~50 lines. Smell above 100.
- **Feature / package README**: ~30–60 lines. Smell above 80.
- **Spec under `docs/<area>/`**: usually ≤200 lines. If it grows toward a folder of its own, split it.

If a doc balloons to match the code, it's restating the code instead of condensing intent.

## Heuristics

- **Code comments** beat **PR descriptions** beat **transient process notes.** Put the explanation
  as close to the affected code as you can justify.
- **README first, AGENTS.md only if there's a workflow rule.** A README explains _what the package
  is_; an `AGENTS.md` explains _what an agent must or must not do here_.
- **Don't write narrative comments.** Comments only when they explain something the code cannot.
- **One source of truth per fact.** If two docs would say the same thing, point one at the other.

## When in doubt

Ask the {{maintainer}} in chat: "this change introduces convention X — per-package README note,
`AGENTS.md` rule, or ADR?" The cost of asking is one message; the cost of the wrong place is a stale
doc nobody trusts.
